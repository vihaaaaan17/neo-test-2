## Problem Statement

Researchers, analysts, and knowledge workers lack a unified environment that bridges manual, highly-trusted source analysis (like NotebookLM) and autonomous deep research (like GPT Researcher or STORM). Current agentic tools often hallucinate, lose citation provenance, or pollute their own reasoning context with noisy logs. Conversely, grounded RAG tools require entirely manual driving. Users face a "fog of war" when organizing massive research state, leading to token bloat, lost evidence, and inability to cleanly rollback or branch hypotheses when a research direction fails.

## Solution

**NeosisLM**: A unified research workspace that integrates NotebookLM-style "Ground Mode" (strict source-grounding) and autonomous "Research Mode" over a single, highly structured shared memory and state fabric. 

Instead of a monolithic database or a generic RAG chain built from scratch, NeosisLM integrates and builds upon proven open-source implementations:
- **Ground Mode (RAG)** is built on top of **Open Notebook**.
- **Research Mode** methodology is adapted from **STORM** and **LangChain Open Deep Research**.

We are explicitly **not** building RAG and deep research loops from scratch. We are adapting these existing systems and wrapping them in a Domain-Driven design defining **6 distinct Memory Systems** (Knowledge, Source, Research, Episodic, Working, User) and **8 distinct State Systems** (Workspace, Research, Plan, Task, Run, Tool, Evidence, Graph, Version). 

All outputs from Ground Mode or Research Mode are strictly **tagged** (e.g. `ground`, `research`) before being pushed to memory, ensuring perfect provenance and tracking of where each memory item originated. The architecture separates internal exhaustive Knowledge Graphs (Neo4j) from curated user-visible Output KGs.

## User Stories

### Foundations & Data Layer (Phase 1)
1. As a researcher, I want to create a Workspace, so that I can isolate my project's data and settings from other investigations.
2. As a user, I want to upload complex documents (PDFs, Webpages), so that they are parsed (via Docling) into structured, chunked, and immutable source snapshots.
3. As a developer, I want all data interactions to use strict Pydantic schemas, so that I can version object contracts without breaking legacy runs.

### Shared Memory & State (Phase 2)
4. As an agent, I want a "Working Memory" that is ephemeral, so that I don't pollute the long-term Knowledge Memory with my intermediate scratchpad thoughts.
5. As a researcher, I want the system to compress past runs into "Episodic Memory", so that agents can recall past failures without injecting 100k tokens of raw logs into the prompt.
6. As a developer, I want all outputs coming from Ground or Research to be explicitly tagged before being pushed to memory, so that memory origin is tracked perfectly.

### Internal KG & Ground Mode (Phase 3)
7. As a researcher, I want to ask a question in "Ground Mode", leveraging the Open Notebook architecture, so that the system generates an answer strictly constrained to the sources I have selected.
8. As a researcher, I want every claim generated by Ground Mode to have explicit citation links (provenance) back to the exact chunk and source snapshot it was derived from.

### Research Mode, Output KG & Versioning (Phase 4)
9. As a researcher, I want to provide a high-level objective and trigger "Research Mode", leveraging STORM and LangChain Open Deep Research methodologies, so that the agent autonomously investigates the web.
10. As a researcher, I want to view a "Research Output KG", so that I can visually explore the curated relationships between findings, evidence, and claims.
11. As a researcher, I want Git-like version control over my workspace, so that I can branch or rollback if an autonomous run goes down a rabbit hole.

### Evaluation & Reliability (Phase 5)
12. As an ML Engineer, I want the system to emit LangSmith traces, so that I can evaluate retrieval precision offline.
13. As a system administrator, I want explicit boundaries (Memory Router) restricting what context enters the prompt, so that I can enforce token budget limits.

### Production Hardening (Phase 6)
14. As a user, I want to export my entire workspace as a portable JSON/Parquet bundle.

## Implementation Decisions

1. **UI Separation**: The final production UI will reside in a dedicated `ui/` folder outside of the `app/` backend directory. This folder will remain empty during the backend build. For testing our backend, we will build very simple testing-type UIs that are completely separate from the `ui/` directory.

2. **Phasing Strategy**:
   - **Phase 1**: Foundations (Postgres, S3, Pydantic contracts).
   - **Phase 2**: Memory & State Fabric (Tagged memory routing, LangGraph reducers).
   - **Phase 3**: Internal KG & Ground Mode (Adapting Open Notebook for grounded QA).
   - **Phase 4**: Research Mode & Curated Graph (Adapting STORM/Open Deep Research workflows).
   - **Phase 5**: Evaluation & Async.
   - **Phase 6**: Production Hardening.

3. **Reuse Strategy (Do NOT Rebuild from Scratch)**:
   - We will maintain a `references/` folder locally containing clones of the core upstream OSS repositories (`open-notebook`, `storm`, `open_deep_research`, `gpt-researcher`).
   - We will extract and adapt code from these repos for RAG and autonomous loops rather than reinventing them.
   - The primary engineering focus is on building the shared Memory Fabric, State Engine, graph projectors, and provenance wrappers around these OSS bases.

4. **Memory Tagging Requirement**:
   - Any data generated by Ground Mode or Research Mode must be tagged (e.g., `source_mode="ground" | "research"`) before being pushed to canonical memory to preserve the context of its creation. This ensures that memory origin is tracked perfectly.

5. **Architectural Patterns**:
   - **Ports and Adapters**: Infrastructure is hidden behind interfaces (`ProviderAdapter`, `GraphStore`).
   - **Canonical Relational Truth**: PostgreSQL is the single source of canonical truth. Neo4j graphs are projections.

### Phase 3 Specific Implementation Decisions (Internal KG & Ground Mode)

1. **Graph Database Provider**: The Internal KG will be backed by a **local Docker Neo4j** container for the free-tier and local development. This ensures zero-cost local sandboxing while keeping the door open for Neo4j Aura at scale.
2. **Ground Mode Orchestration**: Ground Mode will use a **simplified LangGraph** (e.g., Retrieve -> Validate -> Answer). This bypasses the heavy autonomous loop but maintains architectural consistency with the `WorkingMemory` state engine used in Research Mode.
3. **Hybrid Retrieval**: Retrieval will combine **Postgres Full-Text Search (FTS)** and **`pgvector`**. To ensure this is scalable to 1000 users without standing up Elasticsearch, we will heavily index the FTS TSVECTOR columns and strictly scope all queries by `workspace_id`.
4. **Provenance Enforcement**: Ground Mode outputs will use **Structured JSON (Pydantic)** to enforce provenance. Responses will strictly decouple the generated prose from a structured `list[EvidenceRef]` pointing back to precise Neo4j node IDs and Postgres chunk IDs.
5. **Graph Synchronization**: Neo4j is a projection of Postgres. Synchronization will be handled asynchronously using the **`arq` background job queue** (built in Phase 2.5). The API will write to Postgres, enqueue a sync job, and return, preventing API latency spikes during complex entity extraction.

## Testing Decisions
- Testing will target the highest seam possible (e.g., Domain Service Interfaces).
- Evaluation via LangSmith for groundedness and citation coverage.

## Out of Scope
- **Production Frontend UI**: The main frontend UI is currently out of scope and will be developed later in a separate `ui/` folder. During backend implementation, we will only build very simple testing UIs (not placed in the `ui/` folder) to validate functionality.
- Custom Agent Framework (relying on LangGraph).
- Building RAG entirely from scratch (relying on Open Notebook).
- Building autonomous research workflow entirely from scratch (relying on STORM / Open Deep Research).

## Scalability & Concurrency Requirements (1000-User Benchmark)

> **Decision**: The system MUST sustain 1000 concurrent users on a modest deployment (2–4 core VM, Supabase free-tier Postgres, free-tier Redis, single S3 bucket). This section defines the architectural invariants that every component must satisfy. Status: **Locked**.

### 6. **Connection & Pool Management**
   - Every async database engine MUST configure explicit `pool_size`, `max_overflow`, `pool_timeout`, `pool_recycle`, and `pool_pre_ping`.
   - Total pool connections MUST stay below the Postgres provider limit (e.g., Supabase free = 60 direct connections; pool_size + max_overflow ≤ 50, leaving headroom).
   - `echo=True` is FORBIDDEN in any non-development environment. Use a `DEBUG_SQL` config flag.
   - All external clients (S3, Redis, Neo4j, LLM providers) MUST use persistent connection pooling, not per-call instantiation.

### 7. **Multi-Worker Deployment Model**
   - The application MUST run behind a process manager (Gunicorn + UvicornWorker) with ≥2 workers per core.
   - **No module-level mutable singletons**: Any shared mutable state (caches, engines, checkpointers) must be either:
     - Backed by an external store (Postgres, Redis), OR
     - Explicitly designed as per-worker-process state with documented isolation semantics.
   - The `WorkingMemory` checkpointer MUST use a durable backend (`AsyncPostgresSaver` or `RedisSaver`), not in-process `MemorySaver`.

### 8. **Asynchronous Job Queue (Mandatory)**
   - ALL operations exceeding 5 seconds expected wall-time MUST be dispatched to a background job queue.
   - This includes: document parsing (Docling), chunking, episodic memory compression, embedding generation, graph projection, and report generation.
   - The API endpoint MUST return `202 Accepted` with a job ID. Clients poll or subscribe (SSE/WebSocket) for completion.
   - Jobs MUST be idempotent. Re-enqueuing the same job with the same inputs MUST produce the same result without side effects.
   - **Free-tier recommendation**: `arq` (async Redis queue) or Celery with Redis broker.

### 9. **Rate Limiting & Backpressure**
   - Every API endpoint MUST have per-user rate limits (e.g., 60 req/min free tier, 600 req/min paid).
   - LLM gateway calls MUST be bounded by a concurrency semaphore (e.g., max 5 concurrent calls per deployment).
   - LLM calls MUST use retry-with-exponential-backoff (via `tenacity`) with a maximum of 3 attempts.
   - Upload endpoints MUST enforce file size limits (e.g., 50MB free tier) and concurrent upload limits per user.

### 10. **Tenant-Level Resource Quotas**
   - Every resource creation path MUST check quotas before proceeding:
     - Max workspaces per user.
     - Max sources per workspace.
     - Max total storage bytes per workspace.
     - Max knowledge memory objects per workspace.
     - Max LLM calls per workspace per day.
   - Quotas are stored in a `QuotaService` and configurable via environment or database.

### 11. **Database Index Policy**
   - Every table MUST have indexes on all columns used in WHERE clauses on read-hot paths.
   - Composite indexes MUST exist for tenant-scoped queries (e.g., `(workspace_id, status)`, `(owner_id, created_at)`).
   - Full table scans are FORBIDDEN on any table expected to exceed 1000 rows.
   - Index coverage MUST be validated by `EXPLAIN ANALYZE` on all repository query methods before merging.

### 12. **Caching Strategy**
   - Read-heavy, write-rare data (workspace metadata, source registry, user/workspace memory) MUST be cached.
   - **L1 cache**: Per-process LRU (TTLCache, maxsize=1000, ttl=60s) for hot objects.
   - **L2 cache**: Redis for cross-worker shared cache with short TTLs (30–120s).
   - Cache invalidation MUST happen on writes. Stale reads are acceptable for ≤60s on non-critical paths.

### 13. **Graceful Lifecycle Management**
   - The FastAPI app MUST use a `lifespan` context manager for startup/shutdown.
   - On shutdown: drain job queue, dispose DB engine, flush telemetry, close S3/Redis clients.
   - Health check endpoints MUST verify downstream dependencies (Postgres, Redis, S3) and return `degraded` if any are unreachable.

### 14. **API Versioning & CORS**
   - All routes MUST be prefixed with `/api/v1/`.
   - CORS middleware MUST be configured from application startup.
   - Breaking API changes MUST increment the version prefix.

### 15. **Thread Pool Isolation**
   - CPU-heavy background work (Docling parsing, embedding generation) MUST use a dedicated `ThreadPoolExecutor` separate from the default asyncio executor.
   - The dedicated executor MUST have bounded `max_workers` (e.g., 2 per worker process) to prevent thread starvation.

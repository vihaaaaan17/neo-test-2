# Unified Execution & Chapter 3 Integration

This ADR records the architectural invariants and design decisions for Chapter 4 Phase 4: Unified Execution, Engine Adapters, and Lifecycle Event Bridging.

## Status

Accepted

## Context

Phase 1, 2, and 3 established canonical conversation turns, context assembly policies, working state, deterministic verification, candidate promotion, and timeline epoch fencing. However, the existing execution machinery—the Open Notebook Ground engine and the Open Deep Research (ODR) engine—remained partially decoupled or invoked via legacy bypasses (e.g. direct raw OpenAI calls in `ChatService`, unbridged worker events, or unverified checkpointer fallbacks).

Phase 4 integrates the canonical Chapter 4 product surface with Chapter 3 execution engines under the governing principle:
> **Adapt interfaces. Do not redesign engines.**

## Decisions

### 1. Ground Execution Exclusively Through OpenNotebookGroundEngine
- All Ground execution (both unary and streaming) is routed exclusively through `OpenNotebookGroundEngine`.
- The raw OpenAI client bypass in `ChatService` is eliminated.
- Ground execution receives strictly `workspace_id`, `conversation_id`, `turn_id`, `query`, `source_scope`, and `GroundContext`.
- Ground is strictly forbidden from receiving `ResearchContext`, `KnowledgeMemory`, `ResearchEvidence`, `ResearchReport`, scratchpad state, or derived calculations.
- Mapped citations from Open Notebook are strictly translated back to canonical Neosis source UUIDs.

### 2. ODR Context Ingestion via Structured Message State
- `OpenDeepResearchEngine.astream_events` ingests the canonical, token-budgeted `ResearchContext` generated by Chapter 4 and snapshotted on `ConversationTurn.context_version`.
- The ODR adapter serializes this structured context into an authoritative `RESEARCH CONTEXT AND WORKING STATE` system block prepended to the user objective in initial conversation state.
- The upstream ODR supervisor, researcher nodes, and research graph topology remain untouched.

### 3. Synchronous ResearchEvent to ChatEvent Bridging
- Background workers executing research jobs bridge all state transitions (`planning`, `researching`, `synthesizing`, `candidate.created`, `completed`, `partial`, `cancelled`, `failed`) synchronously into canonical `ChatEvent`s in PostgreSQL via `ChatEventRepository`.
- Each event is simultaneously published to Redis channel `turn_events:{turn_id}` using standardized event constants.
- This guarantees unified real-time SSE streaming and durable replay (`GET /turns/{turn_id}/events`) without race conditions.

### 4. Production Checkpointer Guard and Startup Fail-Fast
- Production environments (`NEOSIS_ENV=production`) strictly require `AsyncPostgresSaver` for both FastAPI and ARQ workers.
- Startup validation verifies connection to PostgreSQL checkpointer storage; failure to initialize aborts process startup immediately (`RuntimeError`).
- In-memory `MemorySaver` is strictly forbidden in production and permitted only in `development` and `test` environments.

### 5. Backward Compatibility via Canonical Turn Delegation
- Legacy and duplicate API endpoints (`/workspaces/{id}/research`, `/ask`, `/chat-ground-mode`) are preserved for backward compatibility but delegate 100% of execution to canonical `ChatService`.
- Legacy routes attach HTTP headers `Deprecation: true` and `Link: </api/v1/workspaces/{workspace_id}/conversations/{conversation_id}/turns>; rel="successor-version"`.
- Orphaned and dead execution helpers (such as standalone `enqueue_research_job()` in `app/api/routes/research.py`) are retired.
